# План AI-части «Аким на 5 часов»

Дата ревизии: 23 сентября 2026 года. Горизонт выполнения: оставшиеся ~2 часа хакатона. Этот файл фиксирует порядок работы для согласования команды; фазы реализации ещё не выполнены.

## 1. Цель и границы продукта

Защитный сценарий: пользователь выбирает ровно пять мероприятий при бюджете 100, получает рассчитанный Astana Quality of Life Score, видит, как изменились пять районов, и понимает разницу между своим выбором и лучшим допустимым набором в **фиксированной конкурсной модели**.

Числа, валидность, лаги, синергии и максимум считает Java backend. AI превращает уже рассчитанные факты в понятное русское объяснение. Пространственные данные Overture дают контекст карты, но не меняют конкурсную формулу и не доказывают причинный эффект мер в реальной Астане.

**Критерий готовности:** пример из датасета даёт Score `56.54307` (на экране `56.54`), содержит сравнение с `bestSolution`, а `explanation.source` становится `llm` при доступном API и `template` при сбое. Пользователь всё равно получает корректные числа.

## 3. Выбранная API-модель

**Основной выбор: OpenAI `gpt-4.1-mini-2025-04-14` через `https://api.openai.com/v1/chat/completions`.** Это фиксированный snapshot модели `gpt-4.1-mini`. По [OpenAI Docs: GPT-4.1 Mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini), модель поддерживает Chat Completions, следует инструкциям, не требует отдельного шага reasoning и рассчитана на низкую задержку. Это позволяет сначала проверить уже написанный Java-клиент с его нынешним форматом запроса. Фактический доступ и скорость **нужно проверить данным API-ключом**; наличие ключа в файле их не подтверждает.

Настройки для демо:

```dotenv
SIMULATION_LLM_URL=https://api.openai.com/v1/chat/completions
SIMULATION_LLM_MODEL=gpt-4.1-mini-2025-04-14
SIMULATION_LLM_TIMEOUT_MS=10000
```

`SIMULATION_LLM_API_KEY` должен получить значение существующего `OPENAI_API_KEY` **на серверной стороне**. Не дублировать значение ключа в Git, примерах, логах или frontend. Для Docker Compose можно передать `SIMULATION_LLM_API_KEY: ${OPENAI_API_KEY}`; для IDE задать переменную процесса. Проверить отдельно, что конфигурация действительно попала в Java-процесс.

`gpt-6-luna` по [текущему руководству OpenAI](https://developers.openai.com/api/docs/guides/model-selection) дешевле и подходит для узких частых задач, но переход на него разумно делать **после рабочего демо** и проверки совместимости параметров текущего Chat Completions клиента. `NVIDIA_API_KEY` остаётся запасным вариантом только после проверки конкретного endpoint и ID модели; сейчас нет основания обещать, что он заработает без изменений. Laya для объяснения и расчёта Score не требуется.

## 5. Контракт AI и проверка качества

Вход модели — только нормализованный сценарий и рассчитанный backend результат. Выход для текущего API — текст `explanation.summary`; `strengths`, `risks`, `recommendations`, Score и `bestSolution` остаются от backend. `source` показывает `llm` только при принятом ответе модели.

Минимальные проверки живого ответа:

1. Непустой русский текст без служебного JSON и выдуманных мер/районов.
2. Любые названные Score, стоимость и дельты совпадают с `SimulationResult`; при сомнении использовать шаблонный числовой заголовок.
3. Лучший набор не называется реальным оптимумом для города, а только максимумом текущей учебной модели.
4. Ошибка, таймаут или отказ API не влияют на валидатор, Score, бюджет и HTTP-ответ с результатом.
5. API-ключ не появляется в Git, frontend, ответе, логах или скриншотах.

## 6. Что сознательно откладываем

- Дообучение Laya: текущие `data/sample/*.jsonl` относятся к обработке обращений, а не к городским сценариям; модель решает типизированные задачи, а не генерирует объяснение. Обучение за два часа не улучшит главное демо.
- RAG/Qdrant/MinIO/Postgres ради AI-объяснения: в конкурсе маленький фиксированный набор данных, который уже включён в backend. История пользователей — отдельная существующая функция backend.
- Новые «реалистичные» коэффициенты на основе Overture: без калибровки с реальными данными это создаст видимость точного прогноза. Возможный отдельный экспериментальный режим — после сдачи базового сценария.
- Генерация презентации и неожиданные события: только если фазы 0–5 завершены и проверены.

## 7. Риски и решения по ним

| Риск                                                   | Действие                                                                                                                    |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Нет доступа к выбранной модели или неверный ключ       | Проверить одним живым запросом в фазе 1. До исправления показывать `template`; сохранить числовой сценарий работоспособным. |
| Первый запрос долгий из-за ленивого глобального поиска | Измерить cold/warm время; для демо прогреть endpoint до показа или оптимизатор при старте, если нужно.                      |
