# Backend симулятора «Аким на 5 часов»

Backend принимает пять выбранных мероприятий, проверяет ограничения и рассчитывает **Astana Quality of Life Score** для шести районов, включая Сарайшык (`saraishyk`). Текущая модель — `v2-saraishyk`; версия HTTP API остаётся `v1`. Frontend получает готовую оценку, изменения по каждому району, использованный бюджет и объяснение результата на русском языке. Отдельные эндпоинты предоставляют справочники и геоданные для карты.

Этот файл описывает текущие контроллеры, модели ответов, правила и сохранённые данные проекта. Примеры предназначены для чтения и интеграции frontend.

## Общие правила API

Локальный адрес по умолчанию: `http://localhost:8080`.

| Свойство | Поведение |
|---|---|
| Основной префикс | `/api/v1` |
| Дополнительные адреса | Только `calculate` и `baseline` доступны также через `/api/simulation/...` |
| Формат обычного ответа | JSON, `Content-Type: application/json` |
| Формат геометрии | GeoJSON, `Content-Type: application/geo+json` |
| Формат ошибок приложения | Problem Details, `Content-Type: application/problem+json` |
| Тело POST | JSON с заголовком `Content-Type: application/json`; создание анонимного профиля — без тела |
| Параметры GET | Без тела; у истории есть `limit` и `offset`, у отдельных ресурсов — `{id}` в пути |
| Авторизация | JWT в `Authorization: Bearer <accessToken>` для `/api/v1/auth/me`, `/api/v1/admin/**` и истории; старый анонимный токен подходит только для истории. Регистрация, вход, расчёт, справочники и карта открыты |
| Пагинация и фильтры | История: `limit=20` (1–100), `offset=0` (≥0); владелец определяется по токену. Справочники и слои карты возвращаются целиком |
| Сохранение сценариев | `POST /api/v1/simulations` рассчитывает и сохраняет снимок в PostgreSQL; `/simulation/calculate` только рассчитывает |
| Повторный расчёт | Каждый запрос начинает с исходного датасета; эффекты прошлых запросов не накапливаются |
| LLM | При настройке API объясняет результат пользователя и лучший набор; без подключения используется шаблон |

В таблицах ниже `number` — JSON-число, `integer` — целое JSON-число, `object<код, number>` — объект с кодами в качестве ключей. Например, `{"T1": 4.5, "T2": 6.75}`.

Коды районов в симуляции: `esil`, `almaty`, `saryarka`, `baikonur`, `nura`, `saraishyk`. Коды мероприятий: `M1`–`M16`. В POST коды регистрозависимы: передавайте `M7` и `saraishyk`. В GET справочника районов `{id}` приводится к нижнему регистру, но пробелы не удаляются. Расширение до шести районов и 16 мер не меняет правило ровно пяти выбранных мероприятий.

## Регистрация и авторизация

Аккаунты и BCrypt-хеши паролей хранятся в PostgreSQL. Для этих маршрутов нужен профиль `postgres`; Compose включает его автоматически. Без БД корректные запросы возвращают `503`. Расчёт симуляции, справочники, карта, Swagger и health остаются публичными. Cookie и серверные сессии для входа не используются.

### POST /api/v1/auth/register

Создаёт аккаунт с ролью `USER`. Авторизация не нужна. Обязательное тело JSON:

```json
{
  "email": "user@example.com",
  "password": "UserPass123!",
  "username": "user"
}
```

| Поле | Тип | Правила |
|---|---|---|
| `email` | string | Непустой корректный email, максимум 254 символа. Пробелы по краям удаляются, регистр приводится к нижнему. Адрес уникален |
| `password` | string | От 8 до 72 символов и не больше 72 байт UTF-8. Пробелы не удаляются; пароль хранится только как BCrypt-хеш |
| `username` | string | От 3 до 50 символов после удаления пробелов по краям; отображаемое имя, для входа используется email |

Ограничение пароля в байтах учитывает BCrypt: кириллица и некоторые другие символы занимают больше одного байта. Поля `role`, `id` и владелец истории назначаются сервером. Передать роль администратора через регистрацию нельзя.

Ответ `201 Created`, объект `AuthResponse`:

```json
{
  "accessToken": "<JWT>",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "user": {
    "id": "11111111-1111-4111-8111-111111111111",
    "email": "user@example.com",
    "username": "user",
    "role": "USER",
    "createdAt": "2026-09-23T10:00:00Z"
  }
}
```

| Поле ответа | Тип | Назначение |
|---|---|---|
| `accessToken` | string | Подписанный JWT для следующих авторизованных запросов |
| `tokenType` | string | Всегда `Bearer` |
| `expiresIn` | integer | Время действия нового токена в секундах, по умолчанию 3600 |
| `user.id` | string, UUID | Постоянный ID аккаунта, к которому привязана история |
| `user.email` | string | Нормализованный email |
| `user.username` | string | Отображаемое имя |
| `user.role` | string | `USER` или `ADMIN`; при регистрации всегда `USER` |
| `user.createdAt` | string, date-time | Время создания аккаунта, UTC |

Повторная регистрация email, включая адрес администратора, возвращает `409 Conflict`. Невалидные поля или JSON — `400`. Ответы ошибок не содержат переданный пароль и его хеш.

### POST /api/v1/auth/login

Авторизация не нужна. Обязательное тело JSON содержит только реквизиты входа:

```json
{"email":"admin@example.com","password":"Admin"}
```

Email нормализуется так же, как при регистрации. Пароль проверяется без удаления пробелов и с учётом регистра. Ответ `200 OK` имеет тот же `AuthResponse`, что и регистрация. Неверный пароль и неизвестный email возвращают одинаковую ошибку `401`; ответ не сообщает, существует ли такой аккаунт. Для заданного локального администратора пароль `Admin` допустим при входе; минимум 8 символов применяется к регистрации новых пользователей.

Каждый вход выдаёт новый JWT того же аккаунта. Новый токен не удаляет историю и не отзывает ранее выданные токены: они действуют до своего срока окончания.

### GET /api/v1/auth/me

Тела нет. Передайте `Authorization: Bearer <JWT>`. Ответ `200` — объект `user` из примера выше, без внешней обёртки и без нового токена. Данные пользователя и его роль берутся из БД. Старый анонимный токен не заменяет вход в аккаунт: действующий анонимный профиль получает здесь `403`.

### GET /api/v1/admin/me

Тела нет. Требует JWT аккаунта с текущей ролью `ADMIN` в БД. Ответ `200` — профиль администратора в том же формате. Зарегистрированный пользователь с ролью `USER` получает `403 Forbidden`; без действующего токена — `401`.

Это защищённый маршрут backend для проверки прав администратора. Отдельного HTML-интерфейса админки этот маршрут не создаёт. Роль администратора не открывает чужую историю: `/simulations` по-прежнему возвращает только сценарии владельца токена.

### JWT и жизненный цикл входа

После регистрации или входа передавайте заголовок:

```http
Authorization: Bearer <accessToken>
```

В Swagger нажмите **Authorize**, выберите **BearerAuth** и вставьте токен без слова `Bearer`. Для проверки можно выполнить вход администратора с примером выше, затем `/api/v1/auth/me` и `/api/v1/admin/me`.

JWT подписывается HMAC SHA-256 (`HS256`). Сервер проверяет подпись, срок `exp`, издателя `iss` (по умолчанию `akim-backend`) и аудиторию `aud` (`akim-api`), затем находит аккаунт в БД. Истёкший, подделанный, некорректный токен или токен отсутствующего аккаунта возвращает `401` с `WWW-Authenticate: Bearer`. JWT не содержит пароль или его хеш. Действующую роль сервер проверяет по БД.

При `401` покажите форму входа и получите новый токен. Refresh-токены, серверный logout/отзыв JWT, подтверждение email, восстановление и смена пароля пока не реализованы. Выход на frontend означает удаление токена на клиенте; уже выданный токен продолжает действовать до `exp`.

### Администратор и настройки JWT

При старте с профилем `postgres` создаётся отсутствующий администратор:

| Параметр | Локальное значение |
|---|---|
| `ADMIN_EMAIL` | `admin@example.com` |
| `ADMIN_PASSWORD` | `Admin` |
| `ADMIN_USERNAME` | `admin` |
| Роль | `ADMIN` |

Начальные реквизиты применяются только при создании. Перезапуск или изменение `ADMIN_PASSWORD` в `.env` не сбрасывает пароль существующего аккаунта. Зарезервированный адрес администратора нельзя занять через публичную регистрацию.

`JWT_SECRET` обязателен для профиля `postgres`: Base64 от минимум 32 случайных байт. `.env.example` содержит готовое значение для локальной проверки. В существующий `.env` добавьте этот параметр; для размещения сгенерируйте собственный секрет и измените начальный пароль администратора. Сохраните один секрет между перезапусками и экземплярами backend: смена секрета делает ранее выданные JWT недействительными, но не удаляет аккаунты и историю. `JWT_TTL_SECONDS` задаёт время действия, по умолчанию 3600 секунд.

### Ошибки регистрации и входа

| HTTP | Причина |
|---|---|
| `400` | Невалидный JSON, отсутствующие или недопустимые поля |
| `401` | Неверные реквизиты входа либо нет действующего JWT для защищённого маршрута |
| `403` | Нет роли ADMIN для административного маршрута либо анонимный профиль пытается открыть /auth/me |
| `409` | Email уже зарегистрирован или зарезервирован для администратора |
| `503` | Профиль postgres выключен или хранилище недоступно |

Ошибки возвращаются в формате `application/problem+json`. Успешные ответы с токенами и профилями не кешируются.

## Районы и показатели

### GET /api/v1/districts

**Назначение:** заполнить список районов, показать исходное состояние города, связать числовые показатели с полигонами карты.

**Запрос:** без параметров и тела. **Ответ:** `200`, массив из шести объектов `DistrictResponse` в порядке `esil`, `almaty`, `saryarka`, `baikonur`, `nura`, `saraishyk`.

| Поле объекта | Тип | Значение и назначение |
|---|---|---|
| `id` | string | Код района; используется в POST и для связи с `properties.district_id` карты |
| `name` | string | Русское название для интерфейса |
| `populationShare` | number | Доля населения в модели; вес района при расчёте `D_avg` |
| `metrics` | object<код, integer> | Десять исходных индексов от 0 до 100 |
| `baselineScore` | number | Исходный балл **района** `D_d`, а не итоговый городской Score |
| `dataProvenance` | DistrictProvenance | Версия модели, синтетические допущения, справочные факты и ссылки на источники |

Основные поля одного элемента массива (поле `dataProvenance` подробно описано ниже):

```json
{
  "id": "nura",
  "name": "Нура",
  "populationShare": 0.16,
  "metrics": {
    "T1": 55, "T2": 40,
    "E1": 45, "E2": 65,
    "S1": 38, "S2": 35,
    "B1": 55, "B2": 50,
    "C1": 60, "C2": 50
  },
  "baselineScore": 49.18
}
```

### GET /api/v1/districts/{id}

**Назначение:** получить данные только выбранного района. `{id}` — обязательный код района, например `nura`.

**Ответ:** `200`, один объект `DistrictResponse` с полями из таблицы выше, без массива. Если район не найден — `404` с Problem Details. Структура ошибки описана в разделе [Ошибки](#ошибки).

### Полный исходный датасет

| ID | Район | Доля населения | T1 | T2 | E1 | E2 | S1 | S2 | B1 | B2 | C1 | C2 | Балл района D |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `esil` | Есиль | 0.27 | 45 | 62 | 68 | 72 | 48 | 55 | 78 | 60 | 75 | 70 | 62.99 |
| `almaty` | Алматы | 0.126290 | 40 | 75 | 50 | 55 | 60 | 65 | 62 | 52 | 50 | 60 | 57.06 |
| `saryarka` | Сарыарка | 0.20 | 50 | 70 | 42 | 40 | 62 | 68 | 58 | 55 | 45 | 55 | 54.65 |
| `baikonur` | Байконур | 0.13 | 52 | 68 | 55 | 50 | 58 | 60 | 52 | 58 | 55 | 58 | 56.63 |
| `nura` | Нура | 0.16 | 55 | 40 | 45 | 65 | 38 | 35 | 55 | 50 | 60 | 50 | 49.18 |
| `saraishyk` | Сарайшык | 0.113710 | 45 | 60 | 55 | 60 | 48 | 50 | 60 | 50 | 55 | 60 | 54.23 |

Модельные доли в сумме равны 1. Прежние индексы пяти районов сохранены из конкурсного датасета; индексы Сарайшыка заданы вручную как синтетическое расширение. Для разделения прежнего веса Алматы `0.24` использовано отношение планировочных оценок населения на начало 2025 года: Алматы 236 000, Сарайшык 212 490. После округления до шести знаков веса составляют `0.126290` и `0.113710`; это не официальные текущие доли населения. [Источники и ограничения](docs1/saraishyk-research.md).

В профиле `postgres` каталог хранится в таблице `akim.districts` и читается backend при старте. Без этого профиля используются те же шесть записей из `backend-akim/src/main/resources/catalog/districts-v2.json`. Изменение строки БД само по себе не обновляет уже загруженный каталог процесса; правила и происхождение новой модели должны версионироваться. Старые результаты `v1` в истории остаются прежними снимками пяти районов.

### dataProvenance — происхождение данных района

Эта структура присутствует в `DistrictResponse`, `SimulationResult.districts[]` и `bestSolution.districts[]`. Для старых сохранений, созданных до её добавления, поле может быть `null`.

| Поле | Тип | Назначение |
|---|---|---|
| `modelVersion` | string | Версия набора индексов и весов: `v2-saraishyk` |
| `syntheticMetrics` | boolean | `true`: индексы `T1`–`C2` являются синтетическими значениями модели |
| `metricsMethod` | string | Как получены индексы: исходный конкурсный набор либо эвристическое расширение |
| `populationShareMethod` | string | Происхождение модельного веса и способ разделения веса Алматы |
| `metricAssumptions` | object<код, string> | Отдельные пояснения к индексам Сарайшыка; у прежних районов может быть `{}` |
| `facts` | object[] | Справочные факты, отдельно от расчётных индексов |
| `facts[].key`, `value`, `unit` | string | Название факта, значение строкой и единица измерения |
| `facts[].asOf` | string или null | Дата или период факта; `null`, если точная дата не установлена |
| `facts[].sourceId` | string | Ссылка на `sources[].id` |
| `sources` | object[] | Использованные первичные источники |
| `sources[].id`, `title`, `url` | string | Код, название и URL источника |
| `sources[].asOf` | string или null | Подтверждённая дата состояния данных; неизвестная дата остаётся `null` |

Например, справочная площадь Сарайшыка `69.53 km2` и планировочная оценка населения `212490 people` не участвуют в вычислении индексов напрямую. Площадь его полигона Overture `61.4 km2` относится к отдельной геометрии и не выдаётся за официальную площадь. Подробности и расхождения источников указаны в [заметке исследования](docs1/saraishyk-research.md).

## Мероприятия

### GET /api/v1/measures

**Назначение:** показать доступные решения, их стоимость, область действия и эффекты. **Запрос:** без параметров и тела. **Ответ:** `200`, массив из 16 объектов `MeasureResponse`, от `M1` до `M16`.

| Поле | Тип | Значение и назначение |
|---|---|---|
| `id` | string | ID меры, передаётся в `decisions[].measureId` |
| `categoryId` | string | Код направления; по нему проверяется лимит двух мер |
| `categoryName` | string | Название направления на русском |
| `name` | string | Название мероприятия |
| `scope` | string | `district` — один район; `city` — все шесть районов |
| `cost` | integer | Стоимость в условных единицах; для городской меры платится один раз |
| `lagQuarters` | integer | Лаг до начала действия меры, в кварталах |
| `realizationFactor` | number | Доля реализованного эффекта: `(8 - lagQuarters) / 8` |
| `fullEffects` | object<код, integer> | Полные изменения индексов до учёта лага |
| `realizedEffects` | object<код, number> | Изменения после учёта лага, до синергий и ограничения диапазона |
| `contextUrl` | string / null | Для M3 — `/api/v1/measures/M3/context`, для остальных `null` |
| `mapLayerUrl` | string / null | Для M3 — `/api/v1/map/lrt`, для остальных `null`; те же ссылки есть в районном каталоге |

В объектах эффектов перечислены только затрагиваемые показатели. Отсутствие кода означает нулевой эффект. Значения — прибавки к индексу, а не проценты от исходного значения.

```json
{
  "id": "M1",
  "categoryId": "transport",
  "categoryName": "Транспорт",
  "name": "Выделенные полосы для автобусов",
  "scope": "district",
  "cost": 18,
  "lagQuarters": 2,
  "realizationFactor": 0.75,
  "fullEffects": { "T1": 6, "T2": 9 },
  "realizedEffects": { "T1": 4.5, "T2": 6.75 }
}
```

### Данные ЛРТ для M3

`GET /api/v1/measures/M3/context` возвращает `200 application/json`: датированный справочный снимок из
`backend-akim/src/main/resources/measure-data/M3/lrt-context.json`, включённый в JAR и Docker-образ.
Сеть и БД при запросе не требуются. Для мер без справки, например `/api/v1/measures/M1/context`, ответ `404`.

| Поле | Назначение |
|---|---|
| `measureId`, `verifiedAt` | `M3` и дата проверки источников (не дата обновления каждого факта) |
| `facts[]` | `id`, русское `label`, `value`, `unit`, `status`, `asOf`, `sourceIds` и при необходимости `note` |
| `route` | Конечные пункты и описание коридора первой очереди с источником |
| `expansion` | План второй очереди и отдельные датированные свидетельства о начале работ и слушаниях |
| `map` | Ссылка на GeoJSON, источник, лицензия и `coverage: "partial"` |
| `simulationUsage` | `affectsScore: false` и назначение справки |
| `sources[]` | `id`, издатель, URL, дата публикации (либо `null` с пояснением), дата доступа |

`value` бывает числом, строкой либо диапазоном `{min, max}`. `comparison: "gt"` означает строго больше указанного
значения, `approximate: true` — приблизительную величину. `reported_actual` — факт из датированного сообщения,
`published_specification` — опубликованный параметр системы, `announced` — объявленная величина. Например,
тариф относится к объявлению перед запуском; дата проверки не превращает его в текущий тариф.
`sourceIds` разрешаются по `sources[].id`. Все даты даны в формате `YYYY-MM-DD`.

`GET /api/v1/map/lrt` возвращает `200 application/geo+json`: 31 исходный `LineString` из `roads_main.geojson`,
отобранных по `properties.class = "light_rail"`, с дополнительным `properties.measure_id = "M3"`.
`metadata` содержит атрибуцию, релиз, число объектов, `coverage: "partial"`, `contains_stations: false`,
описание ограничений и приблизительную сумму длин геометрий (48.247 км, включая параллельные пути).
`bbox` задан как `[minLon, minLat, maxLon, maxLat]`. В выгрузке 27 сегментов помечены `esil`, 4 — `saraishyk`;
это не доказывает отсутствие ЛРТ в других районах. Координаты не достроены и не сдвинуты.
Слой также доступен в `/api/v1/map/layers` и `bootstrap.map.lrt`; кеширование обоих новых ответов — 1 час.

Для карточки M3 загрузите `contextUrl` и покажите источники и даты. При включении `mapLayerUrl` укажите
неполноту покрытия и атрибуцию. Не используйте сумму геометрий как официальную длину и не ограничивайте
доступность M3 районами этого слоя. Конкурсные коэффициенты и Score рассчитываются по прежней модели.
Обновление геометрии: `python scripts/prepare_lrt.py`; обновление справки — после проверки источников и дат
в JSON. Затем пересоберите backend. Сохранённые сценарии не пересчитываются.

## Расчёт сценария

### POST /api/v1/simulation/calculate

Дополнительный равнозначный адрес: `POST /api/simulation/calculate`.

**Назначение:** отправить готовый набор решений и получить итоговую оценку. Параметров URL нет. Заголовок: `Content-Type: application/json`.

### Тело запроса

| Поле | Тип | Обязательность и смысл |
|---|---|---|
| `decisions` | object[] | Обязательно; ровно 5 объектов |
| `decisions[].measureId` | string | Обязательно; ID существующего мероприятия |
| `decisions[].districtId` | string или null | Для `district` обязателен существующий район; для `city` поле отсутствует либо равно `null` |

Для городской меры нельзя передавать `"city"`, пустую строку или код района в `districtId`. Пустая строка не равнозначна `null`.

Frontend передаёт только выбор мероприятий и районов. Стоимость, эффекты, бюджет, горизонт и веса backend берёт из своего каталога и правил.

Пример из [simulation-example.json](docs1/simulation-example.json):

```json
{
  "decisions": [
    { "measureId": "M7", "districtId": "nura" },
    { "measureId": "M8", "districtId": "nura" },
    { "measureId": "M10", "districtId": "nura" },
    { "measureId": "M12" },
    { "measureId": "M5", "districtId": "saryarka" }
  ]
}
```

**Успех:** `200`, объект `SimulationResult`. **Нарушение правил:** `422`, причины без Score. **Некорректное тело запроса:** `400`.

### Пример с мероприятием в Сарайшыке

Готовый файл: [docs1/simulation-saraishyk-example.json](docs1/simulation-saraishyk-example.json). В Swagger у `calculate` выберите **«Школа в Сарайшыке: 95 единиц → 54.95216719»**. Запрос подходит для публичного `POST /api/v1/simulation/calculate` и авторизованного `POST /api/v1/simulations`:

```json
{
  "decisions": [
    {"measureId":"M7","districtId":"saraishyk"},
    {"measureId":"M8","districtId":"nura"},
    {"measureId":"M10","districtId":"nura"},
    {"measureId":"M12"},
    {"measureId":"M5","districtId":"saryarka"}
  ]
}
```

Бюджет `95`, Score `54.95216719`, отображаемый результат `54.95`, прирост `2.61974670`. В сравнении с предыдущим примером школа перенесена в Сарайшык: в Нуре показатель `S1` остаётся критическим, поэтому `nCrit = 1`. Это иллюстрирует влияние распределения решений между районами на итоговый Score.

## Все поля результата

### SimulationResult

Эта структура используется и для `calculate`, и для `baseline`.

| Поле | Тип | Что означает и где использовать |
|---|---|---|
| `metricName` | string | Название оценки: `Astana Quality of Life Score` |
| `modelVersion` | string | Версия расчётной модели, сейчас `v2-saraishyk`; сохранения прежней версии содержат `v1` |
| `finalScore` | number | Точная итоговая оценка без промежуточного округления; для сравнения сценариев |
| `displayScore` | number | Итоговая оценка с округлением до 2 знаков; для итоговой карточки |
| `baselineScore` | number | Точная исходная городская оценка `52.33242049` для текущей модели |
| `scoreDelta` | number | `finalScore - baselineScore` |
| `budget` | object | Лимит, потраченная сумма и остаток |
| `horizonQuarters` | integer | Горизонт расчёта, `8` |
| `baseline` | ScoreSummary | Сводка города до мероприятий |
| `summary` | ScoreSummary | Сводка города после мероприятий |
| `districts` | DistrictResult[] | Данные всех шести районов до/после с `dataProvenance` |
| `measureEffects` | MeasureEffect[] | Выбранные меры и их прямые эффекты с учётом лага |
| `synergies` | AppliedSynergy[] | Только сработавшие синергии; пустой массив, если их нет |
| `explanation` | Explanation | Готовое объяснение на русском |
| `bestSolution` | OptimalSolution или null | Лучший набор текущей модели с детализацией; для baseline и старых сохранений может быть null |
| `comparison` | Comparison или null | Разница с максимумом и признак оптимальности пользовательского Score |

`displayScore` остаётся JSON-числом: для обязательного отображения двух десятичных знаков frontend форматирует его при выводе. Дельту округляйте от `scoreDelta`, а не вычисляйте вычитанием двух уже округлённых оценок.

### budget

| Поле | Тип | Смысл |
|---|---|---|
| `limit` | integer | `100` |
| `spent` | integer | Сумма цен выбранных мероприятий |
| `remaining` | integer | `limit - spent`; не даёт бонусных баллов |

### baseline и summary — ScoreSummary

Оба объекта имеют одинаковую структуру. `baseline` описывает исходное состояние, `summary` — результат сценария.

| Поле | Тип | Смысл |
|---|---|---|
| `dAvg` | number | Средневзвешенный по долям населения балл районов |
| `dMin` | number | Минимальный балл среди шести районов |
| `weakestDistrictId` | string | ID района с минимальным баллом |
| `weakestDistrictName` | string | Название этого района |
| `nCrit` | integer | Количество пар «район × показатель» со значением `< 40` |
| `criticalMetrics` | CriticalMetric[] | Подробный список таких пар |
| `cityContribution` | number | `0.7 × dAvg` |
| `weakestDistrictContribution` | number | `0.3 × dMin` |
| `criticalPenalty` | number | Штраф: `1 × nCrit` |
| `finalScore` | number | `cityContribution + weakestDistrictContribution - criticalPenalty` |

Список `criticalMetrics` считает показатели, а не районы. Например, два критических показателя в Нуре дают `nCrit = 2`.

### criticalMetrics[] — CriticalMetric

| Поле | Тип | Смысл |
|---|---|---|
| `districtId` | string | Код района |
| `districtName` | string | Название района |
| `metric` | string | Код показателя |
| `value` | number | Его значение в соответствующем состоянии модели |

Исходный список:

```json
[
  { "districtId": "nura", "districtName": "Нура", "metric": "S1", "value": 38 },
  { "districtId": "nura", "districtName": "Нура", "metric": "S2", "value": 35 }
]
```

### districts[] — DistrictResult

| Поле | Тип | Смысл |
|---|---|---|
| `id` | string | Код района; для связи с картой |
| `name` | string | Название района |
| `populationShare` | number | Вес района в среднем по городу |
| `before` | object<код, number> | Все 10 исходных показателей |
| `after` | object<код, number> | Все 10 показателей после мер, синергий и clip |
| `metricDeltas` | object<код, number> | Для каждого показателя `after - before`, включая нулевые изменения |
| `scoreBefore` | number | Исходный взвешенный балл района |
| `scoreAfter` | number | Взвешенный балл района после изменений |
| `scoreDelta` | number | `scoreAfter - scoreBefore` для этого района |
| `dataProvenance` | DistrictProvenance или null | Происхождение исходных индексов и веса; у старых снимков может отсутствовать |

Все шесть районов присутствуют даже тогда, когда в части из них ничего не изменилось. Порядок: Есиль, Алматы, Сарыарка, Байконур, Нура, Сарайшык. Для идентификации используйте `id`, а не позицию в массиве. `districts[].dataProvenance` содержит ту же структуру происхождения, что и район в каталоге; она сохраняется вместе со снимком результата.

### measureEffects[] — MeasureEffect

| Поле | Тип | Смысл |
|---|---|---|
| `measureId` | string | ID выбранной меры |
| `name` | string | Название меры |
| `categoryId` | string | Код направления |
| `scope` | string | `district` или `city` |
| `targetDistrictId` | string или null | Выбранный район; для городской меры `null` |
| `cost` | integer | Стоимость меры |
| `lagQuarters` | integer | Лаг меры |
| `realizationFactor` | number | Доля эффекта с учётом лага |
| `affectedDistrictIds` | string[] | Районы, в каждом из которых действует мера |
| `realizedEffects` | object<код, number> | Прибавки к показателям каждого затронутого района до clip и синергий |
| `districtScoreContributionBeforeClip` | number | Сумма `realizedEffects[k] × weight[k]` в одном затронутом районе |

Список отсортирован по числовой части ID меры, поэтому может отличаться от порядка решений в запросе. Для примера: `M5`, `M7`, `M8`, `M10`, `M12`.

`districtScoreContributionBeforeClip` **не является вкладом в итоговый городской Score**. Он не учитывает ограничение значений, синергии, долю населения, изменение самого слабого района и критические штрафы. У городской меры этот прямой вклад применяется отдельно к каждому району. Для фактических изменений используйте `districts[].metricDeltas` и `districts[].scoreDelta`.

Пример объекта для `M10` в Нуре:

```json
{
  "measureId": "M10",
  "name": "Освещение и камеры (расширение Safe City)",
  "categoryId": "safety",
  "scope": "district",
  "targetDistrictId": "nura",
  "cost": 12,
  "lagQuarters": 1,
  "realizationFactor": 0.875,
  "affectedDistrictIds": ["nura"],
  "realizedEffects": { "B1": 10.5, "B2": 1.75 },
  "districtScoreContributionBeforeClip": 1.1025
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `measureIds` | string[] | Две меры, образовавшие синергию |
| `districtId` | string | Район, куда добавлен бонус |
| `metric` | string | Код показателя |
| `bonus` | number | Фиксированная прибавка до итогового clip; лагом не уменьшается |

### explanation — Explanation

| Поле | Тип | Смысл и применение |
|---|---|---|
| `source` | string | Сейчас всегда `template`; позволяет показать способ получения объяснения |
| `summary` | string | Резюме: Score, база, изменение, средний балл, слабый район, критические показатели и бюджет |
| `strengths` | string[] | Улучшения районов, сработавшие синергии, устранённые критические показатели |
| `risks` | string[] | Оставшиеся критические значения, снижение отдельных показателей, пояснение лага и границ синтетической модели |
| `recommendations` | string[] | Советы для сравнения следующего набора решений |

Объяснение использует готовые числа `ScoreCalculator`. Для завершённого сценария оно также включает сравнение с лучшим набором; при настроенном LLM поле `summary` формирует модель, иначе используется шаблон. Для `baseline` остаётся шаблон без поиска оптимума и обращения к LLM. Числа результата от текста объяснения не зависят.

|---|---|
| `finalScore`, `baselineScore` | `52.33242049` |
| `displayScore` | `52.33` |
| `scoreDelta` | `0` |
| `budget` | `{"limit":100,"spent":0,"remaining":100}` |
| `horizonQuarters` | `8` |
| `baseline`, `summary` | Одинаковые сводки исходного города |
| `summary.dAvg` | `56.5406007` |
| `summary.dMin` | `49.18` |
| `summary.weakestDistrictId` | `nura` |
| `summary.nCrit` | `2` |
| `summary.cityContribution` | `39.57842049` |
| `summary.weakestDistrictContribution` | `14.754` |

## Сохранение и история

Операции сохранения и истории работают с PostgreSQL. Compose включает нужный профиль `postgres`; без него операции видны в Swagger, но возвращают `503`. Для нового аккаунта получите JWT через `/auth/register` или `/auth/login`. Предварительный расчёт `/api/v1/simulation/calculate` остаётся доступен без БД и ничего не сохраняет.

Последовательность сохранения:

```text
Authorization → профиль пользователя
5 выбранных решений → Validator → ScoreCalculator → Optimizer → сравнение → LLM/шаблон
→ полный SimulationResult
→ INSERT в PostgreSQL → COMMIT → HTTP 201 с сохранённым результатом
```

`result.bestSolution` содержит глобально лучший допустимый набор, а `result.comparison` — разницу Score и признак оптимальности выбора пользователя. При настройке `SIMULATION_LLM_URL` и `SIMULATION_LLM_MODEL` сервер отправляет оба результата LLM, и `result.explanation.source` становится `llm`; при отсутствии подключения или сбое используется `template`. Полученное объяснение сохраняется вместе с числами и не генерируется заново при чтении истории. Старые снимки читаются с `bestSolution = null`, `comparison = null`.

Проверка пользователя выполняется до расчёта. Поиск и ожидание LLM проходят без открытой транзакции БД; короткая транзакция охватывает только сохранение готового снимка.

Невалидные сценарии возвращают `422` и не создают запись. Ошибка хранилища возвращает `503`, успешный ответ до завершения транзакции не отправляется. После обрыва соединения ответ может потеряться уже после фиксации транзакции: перед повторной отправкой следует проверить историю. Защиты от повторных POST пока нет — каждый успешный запрос создаёт новый сценарий.

### POST /api/v1/users/anonymous — совместимость

Старый маршрут создаёт профиль без регистрации и сохранён для совместимости. Для новой интеграции используйте [регистрацию и вход](#регистрация-и-авторизация). Тела и авторизации не требует. Ответ: `201 Created`, `Cache-Control: no-store`.

| Поле ответа | Тип | Назначение |
|---|---|---|
| `userId` | string, UUID | Постоянный идентификатор профиля |
| `accessToken` | string | Случайный секрет из 32 байт в Base64URL, 43 символа; доступ ко всей истории профиля |
| `tokenType` | string | Всегда `Bearer` |
| `createdAt` | string, date-time | Момент создания профиля, UTC |

Токен возвращается только при создании. База хранит SHA-256 от токена, поэтому сервер не может выдать исходный токен повторно. Сам `userId` не даёт доступа и не принимается как средство авторизации.

У анонимного профиля своя отдельная история и бессрочный токен. Вход по email относится к зарегистрированным аккаунтам; перенос прежней анонимной истории в аккаунт пока не реализован. Существующие анонимные токены и записи сохраняются после миграции БД. Создание нового профиля даёт пустую историю; восстановления потерянного анонимного токена и его отзыва пока нет.

Для трёх операций со сценариями передавайте JWT аккаунта или прежний анонимный токен в одинаковом заголовке:

```http
Authorization: Bearer <accessToken>
```

В Swagger нажмите **Authorize**: для JWT используйте **BearerAuth**, для старого анонимного токена — **AnonymousBearer**. Авторизуйте только нужную схему, вставляя значение `accessToken` без префикса. Отсутствующий, неверно оформленный и неизвестный токен дают `401` с `WWW-Authenticate: Bearer`. Анонимный токен не открывает `/auth/me` и `/admin/me`.

### POST /api/v1/simulations

Принимает тот же `SimulationRequest`, что и `/calculate`:

```json
{
  "decisions": [
    {"measureId": "M7", "districtId": "nura"},
    {"measureId": "M8", "districtId": "nura"},
    {"measureId": "M10", "districtId": "nura"},
    {"measureId": "M12"},
    {"measureId": "M5", "districtId": "saryarka"}
  ]
}
```

Проверяет все ограничения текущей модели и возвращает `201 Created` с объектом `SavedSimulationResponse`. `Location: /api/v1/simulations/{id}` указывает маршрут чтения. Ответ не кешируется (`Cache-Control: no-store`). CORS разрешает frontend читать заголовок `Location`.

| Поле ответа | Тип | Что хранится |
|---|---|---|
| `id` | string, UUID | Идентификатор сохранённого сценария |
| `userId` | string, UUID | Профиль, определённый по токену |
| `createdAt` | string, date-time | Время создания записи, UTC |
| `request` | SimulationRequest | Пять исходных решений в порядке запроса, включая выбранные районы |
| `result` | SimulationResult | Полный объект из раздела «Все поля результата» |

`result` содержит версию модели, бюджет, базовые показатели, показатели после применения мер, эффекты с lag, синергии, самый слабый район, critical metrics, Score, прирост и объяснение. Для исходного примера `result.finalScore = 56.31781049`, `result.baselineScore = 52.33242049`, `result.scoreDelta = 3.98539`, `result.budget.spent = 95`.

Это отдельный снимок: следующие расчёты снова начинаются с исходных данных, прошлые решения не накапливаются. Клиент не передаёт готовый Score — его рассчитывает сервер. При последующем изменении модели старые результаты не пересчитываются. Поэтому в одной истории допустимы записи `v1` с пятью районами и `v2-saraishyk` с шестью: сравнивайте их с учётом версии исходных данных. `dataProvenance` у старых записей может отсутствовать или быть `null`.

### GET /api/v1/simulations

Возвращает историю только текущего профиля. Тела запроса нет.

| Query-параметр | Тип | По умолчанию | Ограничение |
|---|---|---|---|
| `limit` | integer | `20` | От 1 до 100 |
| `offset` | integer, int64 | `0` | Не меньше 0 |

Пример: `GET /api/v1/simulations?limit=20&offset=0`. Ответ `200 OK`:

```json
{
  "items": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "createdAt": "2026-09-23T10:00:00Z",
      "modelVersion": "v2-saraishyk",
      "finalScore": 56.31781049,
      "baselineScore": 52.33242049,
      "scoreDelta": 3.98539,
      "budgetSpent": 95
    }
  ],
  "limit": 20,
  "offset": 0,
  "hasMore": false
}
```

| Поле | Назначение |
|---|---|
| `items` | Массив кратких записей; пустая история возвращает `[]` |
| `items[].id` | UUID для запроса полного сценария |
| `items[].createdAt` | Время создания сценария, UTC |
| `items[].modelVersion` | Версия модели при сохранении |
| `items[].finalScore` | Точный итоговый Score без округления для интерфейса |
| `items[].baselineScore` | Базовый Score той же версии модели |
| `items[].scoreDelta` | Разница между итоговым и базовым Score |
| `items[].budgetSpent` | Потраченные бюджетные единицы |
| `limit`, `offset` | Параметры текущей страницы |
| `hasMore` | Есть ли ещё записи после текущей страницы |

Сортировка: `createdAt DESC`, затем `id DESC` для совпавшего времени. Следующая страница — `offset + items.length`, если `hasMore = true`. При сохранении новых сценариев между загрузками страниц смещения меняются; после сохранения обновляйте историю с `offset=0`. `total` не вычисляется. `userId` не является фильтром: отправка чужого идентификатора не меняет владельца из токена.

### GET /api/v1/simulations/{id}

Принимает UUID сценария и токен текущего профиля. Возвращает `200 OK` с тем же `SavedSimulationResponse`, что и запрос сохранения. Данные берутся из БД; калькулятор и объяснение повторно не вызываются. Чужой и отсутствующий сценарии одинаково возвращают `404`. Неверный формат UUID возвращает `400`.

### Ошибки сохранения и истории

| HTTP | Причина |
|---|---|
| `400` | Невалидный JSON, отсутствующее тело сохранения, неверный UUID или параметры страницы |
| `401` | Нет действующего токена профиля |
| `404` | У текущего профиля нет сценария с таким UUID |
| `422` | Нарушены правила пяти решений; `errors` совпадает с форматом `/calculate` |
| `503` | Профиль `postgres` отключён либо операция с БД завершилась ошибкой |

Формат ошибок — Problem Details. Токены, SQL и реквизиты БД в ответы не включаются.

### Пример для frontend

Вызов `saveSelection` можно привязать к кнопке «Сохранить». Пример использует API контейнера на порту 8081, регистрацию или вход по форме и JWT в памяти страницы. После перезагрузки страницы нужно снова войти; историю это не удаляет:

```javascript
const API = "http://localhost:8081/api/v1";
let accessToken;

async function request(path, options = {}) {
  const response = await fetch(`${API}${path}`, options);
  const body = await response.json();
  if (!response.ok) throw Object.assign(new Error(body.detail ?? "Ошибка API"), {
    status: response.status, problem: body
  });
  return body;
}

async function authenticate(mode, credentials) {
  // mode = "register": {email, password, username}; "login": {email, password}.
  if (!["register", "login"].includes(mode)) throw new Error("Неизвестная операция");
  const session = await request(`/auth/${mode}`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(credentials)
  });
  accessToken = session.accessToken;
  return session.user;
}

function authorization() {
  if (!accessToken) throw new Error("Сначала войдите в аккаунт");
  return { Authorization: `Bearer ${accessToken}` };
}

async function saveSelection(decisions) {
  const saved = await request("/simulations", {
    method: "POST",
    headers: { "Content-Type": "application/json", ...authorization() },
    body: JSON.stringify({ decisions })
  });
  // Запись уже подтверждена. saved.result включает bestSolution,
  // comparison и готовое explanation от LLM или шаблона.
  return saved;
}

async function loadHistory(offset = 0) {
  return request(`/simulations?limit=20&offset=${offset}`, {
    headers: authorization()
  });
}

async function loadSaved(id) {
  return request(`/simulations/${encodeURIComponent(id)}`, {
    headers: authorization()
  });
}

function logoutLocally() {
  accessToken = undefined;
}
```

При `401` обработайте ошибку формы и предложите войти повторно в тот же аккаунт. Новый JWT откроет прежнюю историю. Пример не сохраняет пароль и не создаёт анонимный профиль автоматически. Ключ внешнего LLM остаётся на backend. Каждый новый сценарий сравнивается с глобальным максимумом модели; сравнение двух произвольных записей истории пока не реализовано.

## Поиск лучшего набора и подключение LLM

Последний запрос симуляции — отправка полного набора из пяти решений. На `calculate` и при сохранении backend сначала проверяет запрос и считает пользовательский Score, затем получает глобальный максимум для того же каталога и правил.

`SimulationOptimizer` перебирает сочетания пяти уникальных мер, отсеивает превышение бюджета 100, лимита двух мер направления и глобальные конфликты. Для оставшихся сочетаний перебирает назначения районов с учётом локальных конфликтов. Целевая функция — точный `0.7 × D_avg + 0.3 × D_min − N_crit`, включая лаги, синергии, отрицательные эффекты и clip. Равенство Score разрешается меньшим бюджетом, затем порядком ID мер и районов. Оптимальность относится к фиксированной синтетической модели, а не к реальной городской политике.

Для текущего каталога из 16 мер и 6 районов проверяются **4 859 952** допустимых варианта. Максимальный Score модели `v2-saraishyk` — **57.01147549** (для интерфейса `57.01`), бюджет `98`: городские M2 и M14, районные M3, M8 и M9 в Нуре. Разница с исходным примером — `0.693665`. Расширение каталога сохранило прежний лучший набор. Результат кешируется в памяти процесса для неизменных правил и данных; новый процесс вычисляет его заново. Победивший набор проходит общий валидатор и `ScoreCalculator`.

| Поле | Содержимое |
|---|---|
| `bestSolution.decisions` | Пять лучших решений; формат подходит для повторного POST |
| `bestSolution.finalScore`, `displayScore`, `scoreDelta` | Точный максимум, отображаемое округление и прирост к базе |
| `bestSolution.budget`, `summary`, `districts`, `measureEffects`, `synergies` | Полный числовой разбор лучшего набора |
| `bestSolution.algorithm`, `provenOptimal`, `evaluatedCandidates` | `exhaustive-search`, `true`, число проверенных допустимых вариантов |
| `comparison.scoreGap` | `bestSolution.finalScore − finalScore`, без округления |
| `comparison.isOptimal` | Score пользователя совпадает с максимумом; наборы могут различаться |

`baseline` не вызывает оптимизатор или LLM; оба новых поля равны `null`.

Переменные окружения: `SIMULATION_LLM_URL` — полный URL chat-completions endpoint, `SIMULATION_LLM_MODEL` — ID модели, `SIMULATION_LLM_API_KEY` — необязательный ключ для локального сервера, `SIMULATION_LLM_TIMEOUT_MS` — таймаут в миллисекундах (по умолчанию 10000). Docker Compose передаёт их из `.env`; при запуске из IDE задайте их в конфигурации запуска.

Один запрос LLM содержит правила, нормализованный выбор пользователя и результат с лучшим набором и сравнением. Модель формирует русское резюме; `strengths`, `risks` и `recommendations` остаются детерминированными. Числовые поля нельзя заменить ответом модели. При отсутствующей настройке, таймауте, HTTP-ошибке или некорректном ответе возвращается объяснение по шаблону вместе со сравнением. Текущий Laya `/v1/systemone` не поддерживает этот протокол генерации текста.

## Формула и ограничения

### Условия допустимого сценария

1. Ровно пять решений.
2. Общая стоимость не больше 100; ровно 100 допустимо.
3. Каждая мера выбирается максимум один раз, даже если районы разные.
4. Не больше двух мер одного направления. Выбирать по одной из каждого направления не обязательно.
5. Для районной меры выбран существующий район, для городской район не указан.
6. Нет несовместимых сочетаний.

Остаток бюджета не даёт бонуса. Городская мера занимает одно из пяти решений и оплачивается один раз. Порядок выбора не влияет на вычисления.

### Синергии

| Пара | Дополнительный эффект | Где применяется |
|---|---|---|
| M1 + M2 | T1 +2 | В районе M1 |
| M10 + M12 | B1 +2 | В районе M10 |
| M5 + M6 | E2 +2 | В районе M5 |

Бонус возникает, только если выбраны обе меры. Он фиксированный и не умножается на долю реализации эффекта.

### Конфликты

| Пара | Область запрета | Причина |
|---|---|---|
| M1 + M3 | Любые районы | Либо BRT, либо ЛРТ |
| M4 + M7 | Только один и тот же район | Конфликт за участок |
| M5 + M13 | Только один и тот же район | Дублирование программы |

M4 и M7 в разных районах разрешены. То же относится к M5 и M13. M1 и M3 нельзя выбрать вместе даже в разных районах.

### Порядок вычислений

Обозначения: `d` — район, `k` — показатель, `m` — выбранная мера, `L_m` — лаг меры, `pop_d` — доля населения района, `w_k` — вес показателя.

```text
H = 8
realizationFactor_m = (8 - L_m) / 8

I'_dk = clip(I_dk + Σ(fullEffect_mk × realizationFactor_m) + synergy_dk, 0, 100)

D_d = Σ(w_k × I'_dk)
D_avg = Σ(pop_d × D_d)
D_min = min(D_d)
N_crit = количество пар (d, k), где I'_dk < 40

FINAL SCORE = 0.7 × D_avg + 0.3 × D_min - 1 × N_crit
```

Сумма эффектов включает только меры, затрагивающие данный район. Сначала складываются все эффекты и синергии, затем применяется `clip`: ниже 0 становится 0, выше 100 становится 100. Сам итоговый Score дополнительно не обрезается.

Порог критичности строгий: `39.99` ниже порога, `40` уже не критическое значение. Штраф считается после эффектов, синергий и clip.

Расчёт выполняется через `BigDecimal`, без промежуточного округления. Только `displayScore` и числа в объяснении округляются до двух знаков по `HALF_UP`. Исходные баллы районов калькулятор вычисляет по показателям, а не берёт из заранее записанного `DistrictResponse.baselineScore`.

## Ошибки

### HTTP 422 — невалидный сценарий

При нарушении правил `calculate` возвращает `application/problem+json`. У такого ответа нет `finalScore`, `summary` и результата симуляции.

```json
{
  "type": "about:blank",
  "title": "Невалидный сценарий",
  "status": 422,
  "detail": "Набор решений невалиден. Score не рассчитан.",
  "instance": "/api/simulation/calculate",
  "errors": [
    {
      "code": "DECISION_COUNT",
      "field": "decisions",
      "message": "Нужно выбрать ровно 5 мероприятий"
    }
  ]
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `type` | string | URI типа ошибки; для текущих ошибок обычно `about:blank` |
| `title` | string | Краткое название |
| `status` | integer | HTTP-статус |
| `detail` | string | Общее объяснение |
| `instance` | string | Путь запроса, вызвавшего ошибку |
| `errors` | object[] | Детальные нарушения; расширение ответа именно для валидации сценария |
| `errors[].code` | string | Машинный код для логики frontend |
| `errors[].field` | string | Поле запроса, например `decisions[0].districtId`; индексы начинаются с 0 |
| `errors[].message` | string | Текст причины для пользователя |

Полный список кодов валидатора:

| code | Когда возникает | field |
|---|---|---|
| `DECISION_COUNT` | `decisions` отсутствует, равен null или содержит не 5 элементов | `decisions` |
| `MEASURE_REQUIRED` | Элемент массива null; `measureId` отсутствует, null или пустой | `decisions[i].measureId` |
| `UNKNOWN_MEASURE` | ID не найден в каталоге, включая неправильный регистр | `decisions[i].measureId` |
| `DUPLICATE_MEASURE` | Мера уже встречалась в наборе | `decisions[i].measureId` |
| `CITY_DISTRICT_FORBIDDEN` | Для городской меры передан ненулевой `districtId`, включая пустую строку | `decisions[i].districtId` |
| `DISTRICT_REQUIRED` | У районной меры район отсутствует, null или пустой | `decisions[i].districtId` |
| `UNKNOWN_DISTRICT` | Район районной меры не найден | `decisions[i].districtId` |
| `BUDGET_EXCEEDED` | Стоимость превышает 100 | `decisions` |
| `CATEGORY_LIMIT` | Более двух мер одного направления | `decisions` |
| `CONFLICT` | Найдена запрещённая пара | `decisions` |

При неправильном числе решений валидатор сразу возвращает `DECISION_COUNT`. Если элементов пять, он собирает нарушения дальнейших проверок; ошибок в одном ответе может быть несколько.

### Другие статусы

| Статус | Где возникает | Причина |
|---|---|---|
| `400` | POST calculate | Повреждённый JSON, отсутствующее тело, тело `null` или несовместимая структура JSON |
| `404` | GET districts/{id}, GET districts/{id}/measures | Неизвестный район |
| `405` | Неподдерживаемый метод для существующего маршрута | Например, попытка POST к справочнику |
| `415` | POST calculate | Неподдерживаемый тип содержимого запроса |
| `500` | Чтение слоя карты или манифеста слоёв | Файл отсутствует в classpath либо не может быть прочитан |

Пример содержимого `detail` при неизвестном районе: `Район с id 'unknown' не найден`. Для отсутствующего файла карты: `Map resource is missing: map-data/astana/имя_файла`.

У стандартных ошибок Spring нет обязательного массива `errors`. Frontend должен сначала проверить HTTP-статус, затем использовать `errors`, если он есть, иначе `detail` или `title`.

### Общая структура GeoJSON

Все шесть географических эндпоинтов возвращают объект `FeatureCollection`:

| Поле | Тип | Смысл |
|---|---|---|
| `type` | string | `FeatureCollection` |
| `features` | object[] | Географические объекты |
| `features[].type` | string | `Feature` |
| `features[].geometry` | object | Геометрия объекта |

## Swagger и OpenAPI

`GET /swagger-ui.html` перенаправляет на HTML-интерфейс `/swagger-ui/index.html`. В нём отображаются операции и модели, а у POST calculate задан готовый пример из конкурсного датасета.

`GET /v3/api-docs` возвращает JSON-схему OpenAPI; `/v3/api-docs.yaml` — её YAML-представление. Они генерируются по контроллерам, Java-моделям и аннотациям. Сохранённая схема [docs1/openapi.yaml](docs1/openapi.yaml) имеет версию OpenAPI `3.1.0`; версия прикладного API указана в `info.version` как `v1`.

Основные разделы схемы:

| Поле | Что содержит |
|---|---|
| `openapi` | Версию формата OpenAPI |
| `info` | Название, описание и версию прикладного API |
| `servers` | Адрес сервера; в сохранённой схеме — localhost:8080 (IDE) и localhost:8081 (Docker) |
| `tags` | Группы операций, включая `Simulation` |
| `paths` | Пути, HTTP-методы, параметры, тела запросов, примеры и ответы |
| `components.schemas` | Модели запросов и ответов, на которые ссылаются операции |

Экспорт — снимок схемы, он не обновляется при редактировании Java-файлов. Поля сырых GeoJSON/JSON-файлов подробнее описаны в этом README: контроллер отдаёт их как байты, поэтому автоматически сгенерированная схема не раскрывает их бизнес-структуру полностью.

## Как frontend использует API

1. Получает `bootstrap`: лимит бюджета, количество решений, правила и ссылки.
2. Загружает `districts` и `measures` для исходных карточек и списка решений.
3. Загружает границу города и полигоны районов. Связывает их с каталогом по `district_id` и `id`.
4. По выбору района использует `/districts/{id}/measures`, чтобы показать область действия каждой меры.
5. Хранит выбранные решения на клиенте; для городской меры не отправляет `districtId`.
6. Отправляет пять решений в `calculate`.
7. При `422` показывает `errors[].message`, выделяя `errors[].field`. При `200` выводит итог и обновляет показатели на карте.
8. Загружает POI, парки и дороги по включению соответствующих слоёв. Фильтрует крупные слои на клиенте.

| Элемент интерфейса | Источник данных |
|---|---|
| Итоговая карточка или карточка для публикации | `metricName`, `displayScore` |
| Прирост относительно базы | `scoreDelta`, отформатированный до нужной точности |
| Полоса бюджета | `budget.spent`, `budget.limit`, `budget.remaining` |
| Общая оценка города | `summary.dAvg` |
| Самый слабый район | `summary.weakestDistrictName`, `summary.dMin` |
| Проблемные показатели | `summary.criticalMetrics` |
| Цвет района после расчёта | `districts[].scoreAfter` |
| Изменение цвета или подпись улучшения | `districts[].scoreDelta` |
| Таблица показателей до/после | `districts[].before`, `after`, `metricDeltas` |
| Список выбранных мер и задержек | `measureEffects` |
| Бонусы сочетаний | `synergies` |
| Объяснение, сильные стороны, риски | `explanation` |

Frontend может заранее проверять ограничения для удобства пользователя, но окончательное решение о валидности принимает backend. Числа итогового Score следует брать из ответа API.

## PostgreSQL и Docker Desktop

PostgreSQL уже описан сервисом `postgres` в корневом `compose.yaml`. Сервис `backend-akim` собирает Java-приложение и подключается к этой БД по имени `postgres` внутри общей Docker-сети.

### Запуск двух контейнеров

Откройте Docker Desktop и выполните из корня репозитория:

```powershell
docker compose --env-file .env.example up -d --build backend-akim
```

Будут запущены `backend-akim` и его зависимость `postgres`. Laya, Redis, Qdrant и MinIO для этого соединения не требуются и этой командой не запускаются. В Docker Desktop откройте группу **hack-61391193**. После готовности PostgreSQL стартует Java-backend; оба контейнера должны получить статус **healthy**.

Файл `backend-akim/Dockerfile` собирает JAR внутри Maven/JDK 21 и запускает его в JRE 21. Сборка образа пропускает тесты. `Dockerfile.dockerignore` ограничивает контекст Java-исходниками и семью файлами карты, исключая модели, Parquet и локальные секреты.

Для собственных настроек используйте локальный `.env`, созданный на основе `.env.example`; тогда параметр `--env-file .env.example` можно опустить. `.env` исключён из Git. Не заменяйте уже существующий файл с настройками.

### Адреса и реквизиты для локальной проверки

| Параметр | С компьютера | Между контейнерами |
|---|---|---|
| Backend | `http://localhost:8081` | `http://backend-akim:8080` |
| PostgreSQL host | `localhost` | `postgres` |
| PostgreSQL port | `POSTGRES_PORT`, в примере `5432` | Всегда `5432` |
| База | `POSTGRES_DB`, в примере `hack` | То же значение |
| Пользователь | `POSTGRES_USER`, в примере `hack` | То же значение |
| Пароль | `POSTGRES_PASSWORD` из выбранного env-файла | То же значение |

Пароль в `.env.example` — пример для локальной разработки. Java-backend получает реквизиты через переменные окружения. PostgreSQL хранит данные в volume `postgres-data`, который сохраняется при остановке контейнера. Реквизиты `POSTGRES_*` инициализируют новую базу при первом создании её каталога данных; изменение env-файла не меняет пользователя и пароль в уже существующей базе.

### Проверка в браузере

Откройте [http://localhost:8081/actuator/health/db](http://localhost:8081/actuator/health/db). Ожидаемый ответ при успешном соединении:

```json

```

Этот же маршрут используется healthcheck контейнера Java. Он проверяет доступность БД через настроенный datasource. Одного успешного `pg_isready` у PostgreSQL недостаточно для подтверждения соединения Java — поэтому проверяются оба контейнера.

Общее состояние: [http://localhost:8081/actuator/health](http://localhost:8081/actuator/health). Swagger: [http://localhost:8081/swagger-ui/index.html](http://localhost:8081/swagger-ui/index.html).

### Проверка соединений внутри Docker Desktop

Откройте контейнер **postgres → Exec** и выполните в его терминале:

```sh
psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

В открывшейся SQL-консоли:

```sql
SELECT current_database(), current_user;

SELECT application_name, usename, datname, state
FROM pg_stat_activity
WHERE application_name = 'backend-akim';
```

Подключения Java помечены именем `backend-akim`. Состояние `idle` нормально: соединение открыто в пуле и ждёт следующего запроса. Для выхода из `psql` используйте `\q`.

В контейнере **backend-akim → Logs** можно увидеть запуск Spring с профилем `postgres` и сообщения пула `AkimPostgresPool`.

### Java из IDE, PostgreSQL в Docker

Для такого варианта запускается только сервис PostgreSQL:

```powershell
docker compose --env-file .env.example up -d postgres
```

В конфигурации запуска Java задайте `SPRING_PROFILES_ACTIVE=postgres`, `POSTGRES_HOST=localhost`, `POSTGRES_PORT=5432`, `POSTGRES_DB=hack`, `POSTGRES_USER=hack`, `POSTGRES_PASSWORD` и `JWT_SECRET` из того же env-файла. При необходимости задайте `JWT_TTL_SECONDS` и `ADMIN_*`. Если вы изменили порт или реквизиты, используйте свои значения. Spring не читает корневой `.env` автоматически: для IDE эти значения нужно передать в окружение процесса. Сам Java-backend в этом режиме по умолчанию слушает `8080`.

Без профиля `postgres` backend продолжает работать без datasource; `/actuator/health/db` в таком режиме не предоставляется, а операции регистрации, входа, профиля и истории возвращают `503`. С профилем `postgres` включён Flyway. Hibernate `ddl-auto=none` и SQL-init `mode=never` оставлены: таблицами управляют версионированные миграции.

### Таблицы районов, аккаунтов и сохранённых сценариев

Миграции из `backend-akim/src/main/resources/db/migration/` применяются автоматически при запуске backend с профилем `postgres`. V1 создаёт историю и исходные анонимные профили; V2 переименовывает `anonymous_users` в `users` и добавляет поля зарегистрированных аккаунтов; V3 создаёт `districts` и заполняет шесть районов модели `v2-saraishyk` вместе с происхождением данных. Существующие UUID, хеши токенов, сценарии и связь владельца сохраняются. История `v1` не пересчитывается. Flyway использует отдельную схему `akim`; служебная таблица `akim.flyway_schema_history` учитывает выполненные миграции. Повторный запуск сохраняет существующие записи. Механизм подключения соответствует [документации Spring Boot о Flyway](https://docs.spring.io/spring-boot/how-to/data-initialization.html).

| Таблица | Данные |
|---|---|
| `akim.users` | `id` UUID, `email`, `username`, `password_hash` BCrypt, `role`, `created_at`; для старых анонимных профилей — уникальный `token_hash` SHA-256 и пустые поля аккаунта |
| `akim.districts` | `id`, `model_version`, `sort_order`, `name`, `population_share`, `metrics` JSONB, `baseline_score`, `data_provenance` JSONB; шесть исходных районов |
| `akim.simulations` | `id` UUID, `user_id` (внешний ключ профиля), `created_at`, `model_version`, `request` JSONB, `result` JSONB, `final_score`, `baseline_score`, `score_delta`, `budget_spent` |

В `request` сохраняются меры и районы. В `result` хранится весь `SimulationResult`, включая исходные и итоговые показатели. Точные числа дополнительно вынесены в `NUMERIC` без ограничения числа знаков; индекс `(user_id, created_at DESC, id DESC)` обслуживает историю. Эти записи не изменяются API: каждый новый выбор сохраняется отдельным снимком.

`akim.districts` хранит расчётный каталог, а не геометрию. GeoJSON и пространственная статистика читаются из ресурсов JAR. В профиле `postgres` backend выбирает строки текущей версии модели и кеширует каталог при старте; изменения в таблице требуют согласованного обновления модели и перезапуска.

После сохранения примера через Swagger откройте **Docker Desktop → postgres → Exec** и войдите в psql:

```sh
psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

Внутри psql:

```sql
\dt akim.*

SELECT id, name, model_version, population_share, baseline_score
FROM akim.districts
ORDER BY sort_order;

SELECT id, metrics, data_provenance
FROM akim.districts
WHERE id = 'saraishyk';

SELECT id, email, username, role, created_at
FROM akim.users
WHERE email IS NOT NULL
ORDER BY created_at DESC;

SELECT id, user_id, created_at, model_version, final_score, score_delta, budget_spent
FROM akim.simulations
ORDER BY created_at DESC, id DESC
LIMIT 10;

SELECT id, request, result -> 'summary' AS summary
FROM akim.simulations
ORDER BY created_at DESC, id DESC
LIMIT 1;
```

Данные сохраняются в существующем volume `postgres-data` после остановки, перезапуска и пересборки backend. Удаление этого volume удаляет и профили, и историю. При изменении реквизитов уже существующей базы используйте её действующие логин/пароль, а не создавайте новое хранилище ради настройки подключения.

### Проверки реализации

`AuthenticationIntegrationTests` проверяет регистрацию, вход, BCrypt, нормализацию email, ограничения полей, JWT с неверной подписью/сроком/claims, роли, изоляцию истории, совместимость старых токенов и ответ `503` при сбое БД во время авторизации. Используется отдельный PostgreSQL через Testcontainers.

`SimulationHistoryIntegrationTests` проверяет миграцию на отдельном временном PostgreSQL, сохранение и чтение снимка без повторного расчёта, изоляцию профилей, ошибки токенов, отказ при невалидных решениях, пагинацию и откат INSERT при ошибке. Используется [Testcontainers PostgreSQL](https://java.testcontainers.org/modules/databases/postgres/); без доступного Docker эти тесты пропускаются. Тестовая БД не использует volume приложения.

`HistoryWithoutDatabaseTests` проверяет `503` без профиля `postgres`, работоспособность обычного калькулятора и описание Bearer-токена в OpenAPI. Команда запуска всех тестов из `backend-akim` при JDK 21: `./mvnw.cmd test`.

## Настройки и расположение данных

Стек текущего проекта: Java 21, Spring Boot 4.1.1, Spring Web MVC, Spring Security, JWT, BCrypt, springdoc-openapi 3.0.3, Spring Boot Actuator, Flyway. Профиль `postgres` включает JPA/JDBC и драйвер PostgreSQL; аккаунты и история используют JDBC. При работе без этого профиля datasource, Hibernate и Flyway отключены; справочники и расчёты работают без БД. Docker Compose включает профиль автоматически.

Геоданные для Maven и Docker берутся из `data1/overture/astana` и включаются в classpath `map-data/astana/`. Сам сервер читает файлы из собранного приложения. Скрипт `scripts/overture_astana.py` записывает подготовленные данные в этот же каталог; он включает Сарайшык с подтипом `locality`, проверяет наличие шести районов и отсутствие пересечений их внутренних областей.

В сборку включаются `city_boundary.geojson`, `district_stats.json`, `districts.geojson`, `parks.geojson`, `pois.geojson`, `roads_main.geojson`, `lrt.geojson`. CSV статистики и исходные Parquet-файлы не включены в эти API.

Индексы районов, веса и происхождение хранятся в версионированном JSON seed и в `akim.districts`; меры и правила заданы в Java-коде. Изменение Word-документа само по себе не меняет расчёт. При изменении модели нужно согласованно обновлять seed, миграцию БД, правила, версию модели и описание API. Геоданные остаются отдельным источником пространственного контекста.
